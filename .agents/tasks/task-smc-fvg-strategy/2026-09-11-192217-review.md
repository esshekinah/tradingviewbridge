# FVG-in-BOS/CHoCH indicator turned into a limit-order strategy (v1)

`smc_fvg.pine` was copied to `smc_fvg_strategy.pine` and its `indicator()` declaration swapped for a `strategy()` one, adding a trading layer on top of the untouched FVG-in-break engine. When a BOS/CHoCH confirms on candle close and the existing Internal/Swing/Both gate highlights an FVG, the code drops a limit order at that FVG's proximal edge (long = FVG top, short = FVG bottom) with SL/TP expressed in points (300/5000 defaults), and paints a permanent split-rectangle projection (blue TP zone, purple SL zone, dotted entry line). Orders reuse the same gated blocks as the FVG highlight, so the structure selector is the single trade enable. The base indicator file is byte-for-byte unchanged.

**Watch for:** the order cap counts *lifetime* orders, not concurrent ones, so after 100 orders have ever fired no further orders are placed even if all have closed (confirmed); only the *single* most-recent FVG per break is ordered, not "all FVG within the break" as the original request phrased it (confirmed); and SL/TP are treated as raw price units with no `mintick` scaling (confirmed, author-flagged for confirmation).

**Verdict**: NEEDS_CHANGES

## High-level view

The conversion is mechanically clean: one `strategy()` declaration with `pyramiding=100` matching the 100-order cap, `default_qty` set, and `calc_on_every_tick=false` so entries are decided on bar close as specified. `placeStrategyOrder` is defined before `displayStructure` and called only inside the pre-existing `bullMakeFvg`/`bearMakeFvg` blocks, so the Internal/Swing/Both selector genuinely gates trades with no separate toggle — matching item 7.

The concurrency model is the main problem. `tradeOrders` is append-only — nothing ever removes an entry when a limit fills or a position closes — and the cap check is `tradeOrders.size() < maxOrdersInput`. That makes the input a lifetime budget, not the "Max Concurrent Orders" its label promises. On any chart that runs long enough to place 100 orders, order placement silently stops forever.

Two smaller gaps: the engine highlights and therefore orders only the last same-direction FVG in the break leg, which is narrower than "all fvg within bos/choch"; and points are raw price units, which the author deliberately surfaced.

<details>
<summary>Issues (4)</summary>

1. **Cap is lifetime, not concurrent** — `tradeOrders` never shrinks, so `tradeOrders.size() < maxOrdersInput` blocks all new orders once 100 have ever been placed. Either rename the input to reflect lifetime semantics, or prune closed/filled orders (or track a live-position count) so the cap governs concurrent pending orders as the label and item 6 intend.
2. **Only one FVG ordered per break** — `highlightStructFvg` records just the most-recent FVG in the leg, so exactly one order fires per BOS/CHoCH; the original ask was "pending order to all fvg within bos/choch". Confirm whether single-FVG (per clarifying answer 1) is intended or whether every FVG in the leg should get an order.
3. **Points not scaled by mintick** — SL/TP add raw price units to entry; on instruments where 1 point ≠ 1 price unit this is wrong. Author flagged this for user confirmation; resolve before shipping.
4. **`filled` field is dead** — `tradeOrder.filled` is never set true, so it can't drive pruning or projection changes. Wire it up or drop it.

</details>

<details>
<summary>Details</summary>

### Order cap counts placements, not open positions

`placeStrategyOrder` guards on `tradeOrders.size() < maxOrdersInput`, and `tradeOrders.push(...)` runs on every placement while nothing ever calls `tradeOrders.remove(...)` or resets the array. The `filled` flag on the UDT is declared but never assigned, and there is no hook on fill or close. So the cap measures how many orders have *ever* been placed over the whole chart history, not how many are currently pending or open. A strategy that trades actively will hit 100 placements and then stop opening any new position for the rest of the series, even though every earlier order may have filled and closed. The input is labelled "Max Concurrent Orders" and the user asked to "handle multiple pending order as some fvg will form while some pending order are still not yet triggered" — that framing is about live concurrency, so the current behavior diverges from intent. `pyramiding=100` allows 100 simultaneous entries at the engine level, which makes the array cap the sole limiter, and it is limiting the wrong quantity. A fix needs either to prune `tradeOrders` when `strategy.opentrades`/`strategy.closedtrades` indicate an order is done, or to count only unfilled/open ids against the cap.

### Gate reuse and new-FVG detection

The order calls live inside the existing `if bullMakeFvg` / `if bearMakeFvg` blocks, which already fold in `showStructFvgInput` and the Internal/Swing/Both `structFvgSourceInput`. A `structFvgs.size()` before/after comparison around `highlightStructFvg` fires an order only when a new FVG was actually pushed — and because `maintainStructFvgs()` (the only other mutator, which can shrink the array) runs earlier in the bar, the delta cannot be corrupted by a concurrent removal within `displayStructure`. Switching the selector off for internal or swing structure disables the corresponding trades automatically (item 7). Note the narrowing this inherits: `highlightStructFvg` records only the most-recent same-direction FVG in the leg, so at most one order is placed per break — see Watch For.

### Projection budget

None of the projection drawings are ever deleted (item 3). This stays within the `max_boxes_count=500` / `max_lines_count=500` budget: the lifetime cap of 100 orders yields at most 200 boxes and 100 lines, plus the FVG boxes from the engine — the one place the lifetime cap is quietly protective rather than harmful. If the cap is changed to concurrent semantics (issue 1), re-check that projections from long-closed orders don't push the drawing count past 500 on a long series.

</details>
