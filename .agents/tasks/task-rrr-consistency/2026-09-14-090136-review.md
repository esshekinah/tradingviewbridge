# Extend the direction-conflict guard to cover same-bar and pending opposite orders (v2)

`placeStrategyOrder` now blocks an opposing entry not only when the net *filled* position points the other way (`posConflict`) but also when any un-closed tracked order in `tradeOrders` points the other way (`trackedConflict`). A bounded loop scans `tradeOrders` for an `isLong != isBull` entry, and `directionOk = not posConflict and not trackedConflict` is ANDed into the placement `if`. This directly answers both residual reversal-netting paths the v1 review left open: the same-bar internal-long + swing-short pair (the earlier submission is already pushed into `tradeOrders` before the second pass reads it) and the resting pending Limit that has not moved `position_size`. The exit-tick math and every other subsystem are untouched.

**Watch for:** a limit entry that is submitted but *never fills* is never removed from `tradeOrders` — `maintainTradeProjections` prunes only on close (`closedTradeIndex >= 0`), and a never-touched limit is neither open nor closed — so it can linger indefinitely and permanently block every opposite-direction entry (confirmed: no `cancel`/expiry path exists anywhere in the file). Whether this bites depends on how often a limit rests unfilled; in Limit mode (the default) it is plausible over a long session.

**Verdict**: NEEDS_CHANGES

## High-level view

The v2 fix closes both v1 residual paths. `tradeOrders.push` runs synchronously at the end of `placeStrategyOrder`, and the per-bar order is `maintainTradeProjections()` → `displayStructure(true)` → `displayStructure()`, so when the swing pass calls `placeStrategyOrder` the internal pass's order is already in `tradeOrders` and the scan sees it. A resting limit stays in `tradeOrders` (never open, never closed), so it too is visible to the scan. Both same-bar and pending-limit netting are now blocked at submission time rather than relying on filled net position.

The pruning timing is sound for open trades. `maintainTradeProjections` removes an entry only when `closedTradeIndex(id) >= 0`; a still-open opposite trade resolves through `openTradeIndex >= 0` and is kept, so it cannot be pruned prematurely and cause a missed conflict. A closed trade is removed in the same pass that runs before `displayStructure`, so it does not linger to over-block a legitimately-flat book.

The unresolved gap is lifecycle asymmetry for orders that never fill. A market entry always fills and transitions open→closed, so it self-prunes. A limit entry can rest forever without filling, and nothing in the script cancels or expires it; the "still pending => keep" branch keeps it alive for the projection, but the direction guard now also reads that same array, so a stale pending limit becomes a permanent block on the opposite direction. This is a new consequence introduced by scanning `tradeOrders`, not a pre-existing issue.

Over-blocking is otherwise consistent with intent: while any opposite order is open or pending, a new opposing entry submits nothing. That enforces one net direction at a time and reduces trade frequency in two-sided structure — expected, not a regression — but it is now strictly more aggressive than v1 because pending (not just filled) orders block.

Pine v5 constraints hold: the loop is bounded (`0 to tradeOrders.size() - 1`), guarded by a `size() > 0` check, has no `break`/`continue`, reassigns only locals, and the function still ends in the trailing `true`. No global scalar is reassigned inside the function; the change is confined to `placeStrategyOrder` and its doc comment. A re-backtest in TradingView (XAUUSD, SL=4, RRR=10) remains the user's confirmation step and is not a blocker for this static review.

<summary>Details</summary>

### Same-bar and pending-limit paths are both closed

The v1 leak was that `strategy.position_size` reflects only already-filled orders. The v2 scan reads `tradeOrders`, populated by `tradeOrders.push(...)` as the final statement of `placeStrategyOrder`, right after the `strategy.entry`/`strategy.exit` calls. Because the internal and swing passes run sequentially within one bar (`displayStructure(true)` then `displayStructure()`), an internal-pass long is already in `tradeOrders` with `isLong = true` when the swing pass evaluates a short: `trackedConflict` sees `isLong != isBull` and the short is dropped. The across-bar pending-limit case is the same mechanism — a resting limit is in `tradeOrders` regardless of fill state, so a later opposite signal sees it.

```
bar N evaluation order
├─ maintainTradeProjections()   // prunes only orders with closedTradeIndex >= 0
├─ displayStructure(true)        // internal → placeStrategyOrder(true,...)  → tradeOrders.push(L)
└─ displayStructure()            // swing    → placeStrategyOrder(false,...) → scan sees L, blocks
```

### Pruning timing is correct for open and closed trades

`maintainTradeProjections` walks `tradeOrders` and branches on `closedTradeIndex(t.id)` first, then `openTradeIndex(t.id)`; only the closed branch calls `tradeOrders.remove(i)`. A still-open opposite trade takes the `openIdx >= 0` branch and is retained, so the guard cannot miss a conflict against a live opposite position. A trade that closed on a prior bar is removed in this pass — which runs before both `displayStructure` calls — so a legitimately-flat book is not over-blocked by a corpse entry. The one branch that never removes is the trailing "not open and not closed => still a pending limit => keep", which is exactly the lifecycle hole below.

### The pending-limit that never fills is a stuck-state risk

`tradeOrders` is pruned on close and only on close. That is safe for anything that fills, because a filled position eventually closes (SL, TP, or reversal) and gets removed. It is not safe for a limit that never fills. Pine does not auto-expire a resting `strategy.entry` limit, and each order here carries a unique id (`(L|S) + bar_index + '_' + size`), so a new submission never replaces an old resting one. There is no `strategy.cancel` in the file. A limit that rests through the rest of the session stays in `tradeOrders` forever, and the new `trackedConflict` scan turns that permanent residency into a permanent one-directional block: once a stale long limit sits in the array, every future short is refused until end of data.

The guard newly introduces this. In v1 a never-filled limit was invisible to the guard (it did not move `position_size`), so it could not block anything — the v1 review flagged that as a *leak*. v2 fixes the leak but swings to the opposite failure mode, where the same stale order now over-blocks. The correct resolution is a lifecycle for pending limits: remove a pending entry from `tradeOrders` when it is no longer valid (its FVG mitigated/deleted, or after a bounded number of bars), paired with a `strategy.cancel` on the order id so Pine's book and the tracking array stay consistent. Without it, a long backtest in Limit mode can drift into a state where one side is silently frozen out.
