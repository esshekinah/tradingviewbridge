# Expire never-filled limit orders so the direction guard cannot permanently block one side (v3)

The v2 fix scanned `tradeOrders` for any un-closed opposite order and refused the conflicting entry, which closed the same-bar and pending-limit reversal-netting paths but introduced a stuck state: a resting LIMIT that never fills is neither open nor closed, so `maintainTradeProjections` (which pruned only on close) never removed it, leaving it in `tradeOrders` forever and turning the guard into a permanent one-directional block. v3 gives resting limits a bounded lifetime. Two fields are added to the `tradeOrder` UDT (`isLimit`, `submitBar`), a new `limitExpiryInput` input (default 50 bars, `minval = 1`), and the previously comment-only "still pending" case in `maintainTradeProjections` becomes a real `else` branch that calls `strategy.cancel(t.id)` and `tradeOrders.remove(i)` once `bar_index - submitBar > limitExpiryInput`.

**Watch for:** the expiry branch is reached only for orders that are neither open nor closed, gated on `t.isLimit`, so filled/closed and market orders are never wrongly cancelled (confirmed); the downward loop keeps `remove(i)` index-safe (confirmed). The one residual is a design choice, not a bug — `limitExpiryInput` bars is a hard wall unrelated to whether the FVG that spawned the limit is still valid, so a limit can be cancelled while its level is still legitimately resting, or (with a large expiry) block the opposite side for up to 50 bars (possible). Final confirmation still requires a TradingView re-backtest in both Market and Limit modes.

**Verdict**: APPROVED

## High-level view

The stuck state from v2 is resolved. A never-filled limit now falls into a real `else` branch in `maintainTradeProjections` and, once it has rested longer than `limitExpiryInput` bars, is cancelled in Pine's order book and removed from `tradeOrders`, freeing its cap slot and clearing the direction block so the opposite side is no longer frozen out for the rest of the session.

The branch order is what makes the expiry safe: `maintainTradeProjections` tests `closedIdx >= 0` first, then `openIdx >= 0`, and only an order that is neither reaches the expiry `else`. A limit that has filled shows up in `strategy.opentrades` (or `closedtrades`), so an earlier branch claims it before expiry can see it, and the `t.isLimit` guard keeps market orders out of the branch.

The expiry criterion is purely time-based: `limitExpiryInput` counts bars since submission and has nothing to do with whether the FVG level the limit sits at is still valid, so the cancel can fire on a limit that is still a legitimate resting order, and a large expiry keeps blocking the opposite direction for that whole window. This is the intended trade-off (bound the stuck state) rather than a defect, but the value chosen directly sets how aggressively the strategy can flip sides.

A cancelled never-filled limit was never drawn and never entered `closedtrades`, so no projection handle is orphaned and the dashboard stats are untouched. The change stays confined to the four expected touch points.

1. **Time-based expiry is decoupled from FVG validity** (possible) — `limitExpiryInput` cancels a resting limit purely on elapsed bars, regardless of whether its FVG level is still unmitigated and valid. A limit can be cancelled while still legitimately resting (missing a later fill), or, with a high expiry, keep the opposite direction blocked for the full window. Acceptable as a bound; the user should tune the default (50) to their timeframe and, if precision matters, a future pass could tie cancellation to FVG mitigation instead of bar count.
2. **`> limitExpiryInput` gives one extra bar of life** (confirmed, benign) — expiry fires at `bar_index - submitBar > limitExpiryInput`, i.e. on the (submitBar + limitExpiryInput + 1)th bar, so a limit rests `limitExpiryInput + 1` bars. Not an early cancel (safe against clipping a still-resting limit), just off the label's literal reading by one; documenting "expires after N bars" as "removed on the bar after N have elapsed" would be exact.

The user must re-run the XAUUSD backtest (SL=4, RRR=10) once in Market mode and once in Limit mode to confirm surviving trades track the 10:1 distances, that the pending-limit block is now released after expiry, and that trade frequency has not collapsed.

<summary>Details</summary>

### The v2 stuck state is now bounded

v2's guard reads `tradeOrders`, and `maintainTradeProjections` removed an entry only when `closedTradeIndex(id) >= 0`. A limit that never filled took neither the closed nor the open branch, so it sat in `tradeOrders` permanently and the guard blocked every opposite entry until end of data. v3 turns the trailing comment-only case into an executed `else`:

```
per tracked order t (loop runs DOWNWARD: size()-1 .. 0)
├─ closedIdx >= 0        → freeze projection at exit bar, tradeOrders.remove(i)
├─ else if openIdx >= 0  → mark filled, draw/extend projection, keep
└─ else                  → neither open nor closed => resting limit
        └─ if t.isLimit and not na(t.submitBar) and bar_index - t.submitBar > limitExpiryInput
               strategy.cancel(t.id); tradeOrders.remove(i)
```

Once a resting limit ages past `limitExpiryInput`, `strategy.cancel(t.id)` pulls it from Pine's order book and `tradeOrders.remove(i)` drops it from the tracking array. That frees the cap slot (`tradeOrders.size()` shrinks) and, because the direction guard scans that same array, clears the one-directional block.

### Why a filled or closed limit is never wrongly cancelled

The expiry `else` is reachable only when both `openTradeIndex(t.id)` and `closedTradeIndex(t.id)` are `-1` — for a submitted order that means still-pending. A limit that fills becomes an entry in `strategy.opentrades`, so the middle branch claims it; if it has already exited, the closed branch claims it first. So `strategy.cancel` on an id that has actually filled is never reached: the fill routes the order to `openIdx`/`closedIdx` on the same evaluation before the `else` can run. Within the branch, `t.isLimit` excludes market orders (`o.isLimit := not isMarket`), and the `not na(t.submitBar)` clause guards a pre-existing/`na` record from evaluating the arithmetic.

### Timing: a limit that fills on its expiry bar

`maintainTradeProjections()` runs once per bar, before both `displayStructure` passes. On the bar where a limit fills, Pine has already registered it in `strategy.opentrades`, so `openIdx >= 0` is taken and the expiry `else` is not evaluated — the fill wins over expiry, which is the correct precedence, and there is no path where the same bar both fills and cancels the order. The one caveat is the detection lag documented elsewhere in the file: with `calc_on_every_tick = false` a fill is observed when the script next evaluates the order, and during any lag the order still reports pending — but the expiry threshold (default 50 bars) dwarfs the one-bar detection lag, so a genuinely-filling limit is claimed by `openIdx` long before it could age out.

### Boundary and default

`> limitExpiryInput` removes an order submitted at bar S on bar `S + limitExpiryInput + 1`, giving it `limitExpiryInput + 1` bars of life — it never clips a limit still within its nominal window, so there is no off-by-one that cancels too early (see Issue 2 for the label mismatch). `minval = 1` means the smallest configurable expiry still allows at least two bars of rest, so the input cannot cancel a limit on its submit bar. The default of 50 is timeframe-agnostic: on a fast timeframe 50 bars may be too generous (long block windows), on a slow one too tight — worth tuning per instrument/timeframe.

### No collateral damage to projections, cap, or stats

A never-filled limit never reached `drawProjection` (that runs only on the open or closed branch), so at expiry there is no `tpBox`/`slBox`/`entryLine` handle to delete or freeze — the fields are still `na` and removal simply drops the record. The dashboard stats fold only newly *closed* trades from `strategy.closedtrades`; a cancelled never-filled order never entered `closedtrades`, so net points, streaks, and win/loss counts are unaffected — correct, since a never-filled order is not a trade.

### Regression surface for the v1/v2 guard and Pine v5 constraints

`posConflict` (net filled) and `trackedConflict` (scan of `tradeOrders`) are exactly as v2 left them; expiry only removes orders that aged past the window without filling, so a live or recently-submitted opposite order still blocks, and same-direction pyramiding and flat-book entries are unaffected. Pine v5 constraints hold: both touched void functions still end in trailing `true`; the removal loop iterates downward (`tradeOrders.size() - 1 to 0`) so `remove(i)` does not invalidate not-yet-visited indices; there is no `break`/`continue`; the only writes are UDT-field writes on the local `o`, array mutation, and `strategy.cancel` (all legal inside a function), and `limitExpiryInput` is global scope, not reassigned inside a function. These match Pine v5 semantics but cannot be machine-verified without compiling in TradingView — the standard no-toolchain caveat.
