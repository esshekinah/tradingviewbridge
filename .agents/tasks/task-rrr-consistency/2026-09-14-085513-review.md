# Direction-conflict guard to stop reversal-netting from breaking configured R:R (v1)

`placeStrategyOrder` now refuses to submit an entry that points against the currently-open net position. A one-line local guard — `bool directionOk = isBull ? strategy.position_size >= 0 : strategy.position_size <= 0` — is ANDed into the existing placement condition, so a long is only submitted when flat or already long, a short only when flat or already short. This targets the reported symptom on XAUUSD (SL=4, RRR=10, Market): realized per-trade P&L that bore no 10:1 relationship because Pine holds a *single net position* and an opposite `strategy.entry` reversal-closes the open trades at the reversal fill price rather than at their own `from_entry` SL/TP. The exit tick math is untouched; a doc comment now explains both the root cause and the residual, non-code gap slippage.

**Watch for:** the guard reads `strategy.position_size` as-of-now, which reflects already-filled orders but not orders submitted earlier in the *same bar* that have not filled yet — so a same-bar internal-long + swing-short pair, or a pending Limit entry that fills after a later opposite signal is submitted, can still net (confirmed reachable path; whether it fires depends on structure coincidence).

**Verdict**: NEEDS_CHANGES

## High-level view

The core diagnosis is sound. Pine runs one net position; `pyramiding=100` only stacks *same-direction* entries, and an opposite `strategy.entry` flattens the open side at its own fill price and cancels the attached `strategy.exit` orders — which is exactly how a configured 10:1 R:R degrades into the inconsistent, side-split P&L the user saw. Gating placement on position direction is the right shape of fix and keeps every *surviving* trade exiting at its own SL/TP.

The chosen signal, `strategy.position_size`, is the net position after this bar's already-filled orders. The gap is timing: two order submissions within the *same bar* both see the same pre-bar `position_size`, and a pending Limit entry does not move `position_size` until it fills. Neither case is closed by reading net position size at submission time, so a residual reversal-netting path remains — narrower than before, but present. This is why the fix is directionally correct but not yet complete.

A secondary effect: while a position is open, every opposing structure break is dropped rather than queued, so the strategy trades less in choppy two-sided structure — an intended consequence, but the reduced trade count in the re-backtest should not be mistaken for a regression.

The residual instrument-level gap slippage (a 4-point SL smaller than a typical gold bar, with `calc_on_every_tick=false`) is correctly characterized in the comment as a settings reality, not a code bug. Pine v5 constraints are respected: the added statement is a local `bool`, no global scalar is reassigned, no loop or `break`/`continue` is introduced, and the void function still ends in `true`. The change is confined to the placement condition; unrelated subsystems are not touched.

### Why the guard is the right lever

Pine collapses all fills into one net position. With `pyramiding=100`, same-direction signals stack, but an opposite `strategy.entry` does not open a hedge — it closes the open opposite quantity at *that order's* fill price and then flips any remainder. The trades closed this way realize P&L at the reversal price and their attached `strategy.exit` (the `id + '_x'` orders carrying `loss`/`profit`) are cancelled, so their SL/TP never execute. That is precisely the decoupling that produces "all winners on one side, all losers on the other, none near 10:1." Refusing to submit the opposing entry keeps the open trades bound to their own `from_entry` exits. The distance math (`loss = slPointsInput / mintick`, `profit = tpDist / mintick`, `tpDist = rrrInput * slPointsInput` in RRR mode) already preserves the ratio in ticks and is correctly left alone.

`>= 0` / `<= 0` (allowing flat) is the right predicate rather than strict `> 0` / `< 0`: a flat book (`position_size == 0`) satisfies both branches so a fresh entry in either direction is permitted, whereas a strict comparison would have wrongly blocked the first entry from a flat state.

### Where the guard still leaks: same-bar and pending-fill timing

`strategy.position_size` is the net position *as of the current bar's already-filled orders*. It does not reflect an order this script submitted earlier in the same bar evaluation that has not yet filled. Two independent submission paths run every bar:

```
bar N evaluation
├─ displayStructure(true)   // internal → may placeStrategyOrder(true,  ...)  [long]
└─ displayStructure()       // swing    → may placeStrategyOrder(false, ...)  [short]
        │
        └─ both read the SAME strategy.position_size (pre-bar net)
```

If the book is flat entering bar N, an internal bullish break submits a long (guard sees `0`, passes) and, later in the same bar, a swing bearish break submits a short (guard *still* sees `0` because the long has not filled yet, passes). Both orders exist; when they fill, one reverse-nets the other — the exact failure the fix targets, just triggered within one bar instead of across bars. Both `displayStructure` calls are unconditionally evaluated (lines 697 and 700), so this is a confirmed reachable path; how often it fires depends on how often internal and swing structure break in opposite directions on the same bar.

The Limit entry mode widens the same hole across bars: a submitted long limit resting inside an FVG has not moved `position_size`, so a subsequent opposite short signal on a later bar still passes `directionOk`. Both can rest; whichever fills first is then reverse-netted by the other. Reading net *filled* position size cannot see resting orders. Closing these paths needs a guard on *intended/submitted* direction (e.g. a bar-local flag set when an entry is pushed, and/or inspecting pending orders), not solely on `strategy.position_size`.

For Market mode with a position already open and confirmed before the opposing bar, the guard works as intended — likely the majority of the user's reported trades — so this fix should visibly improve consistency even though it is not airtight.

### Cap and projection accounting under the skip

When `directionOk` is false the entire block is skipped, so a dropped opposing signal consumes no cap slot, submits no `strategy.exit`, and creates no projection — `tradeOrders.size()` / `maxOrdersInput` accounting stays honest. The behavioral cost is trade frequency: opposing breaks during an open position are dropped, not queued, so the re-backtest will show fewer trades in two-sided structure. That is intended, not a regression.

### Pine v5 constraints and blast radius

The added line is a local `bool` declaration; no global scalar is reassigned, no loop or `break`/`continue` is introduced, and the function still terminates with the trailing `true` required of a void function. The diff touches only the doc comment and the single placement condition in `placeStrategyOrder`; FVG detection, structure drawing, projection maintenance, dashboard, VWAP filter, and the entry-mode branch are unchanged. The residual instrument-level gap slippage (4-point SL smaller than a typical XAUUSD bar with `calc_on_every_tick=false`, bar assumed SL-first when it spans both levels) is correctly documented as a settings/instrument reality rather than something this code can remove.
